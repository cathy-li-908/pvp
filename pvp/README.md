# pvp —— 【尽伏诛】PVP 插件（OlivOS / 青果）

QQ 群环境下的 **12 人个人群 PVP 对战**插件。每个玩家有一个自己的个人群，PVP 在双方的个人群之间同时进行：各自声明道具、按机器人给的列表逐回合掷骰，机器人自动结算伤害、处理死亡掉落，并向两个群同时播报战报。

- 协议端：**NapCat（OneBot v11）**，同时兼容 QQ 官方机器人通道
- 框架：**OlivOS（青果）**
- 骰子：**OlivaDiceCore**（青果自带，本插件不自己实现掷骰）

## 二、安装

### 1. 放目录

把 `pvp/` 整个目录放到 OlivOS 的插件目录下：

```
<OlivOS>/plugin/pvp/
```

目录名不要改。OlivOS 是**用目录名做 Python 模块名**去 `import` 插件的（`pluginAPI.py` 里 `plugin_module_name = os.path.basename(plugin_dir)`），而本插件内部统一写 `import pvp`；同时 `app.json` 里的 `namespace` 也是 `pvp`，用来定位数据目录 `plugin/data/pvp/`。三者（目录名 / 包名 / namespace）必须一致，改一个就得改全部。

插件在 OlivOS 插件列表里显示的名字是 **`pvp`**，游戏名（尽伏诛）在 `info` 字段和运行时配置里。

### 2. 依赖

| 依赖 | 版本要求 | 说明 |
| --- | --- | --- |
| OlivOS | `svn >= 190` | 见 `app.json` 的 `compatible_svn` |
| OlivaDiceCore | 已安装并正常掷骰（`.ra50` 有反应） | 本插件 `import OlivaDiceCore`，缺了会加载失败 |
| OlivaDiceNativeGUI | 可选 | 装了才能在本插件的自定义回复里看到备注 |

本插件只用 Python 标准库，**不需要 pip 装任何东西**。

### 3. `priority` 为什么是 19990（不要改）

OlivOS 广播一条群消息时，按 `app.json` 里的 `priority` **升序**依次调用各个插件。OlivaDiceCore 的 `priority` 是 `20000`，本插件是 `19990`，所以：

> 同一条群消息，**本插件先拿到，OlivaDiceCore 后拿到**。

这是全部设计的地基。青果的 `.ra` 掷骰结果不通过任何返回值暴露，只能靠两个钩子时机拼出来：

1. 玩家发 `.raN` 时，本插件先收到 → 把这条消息记下来
2. OlivaDiceCore 掷完骰、准备回复时，会调 `msgHook` → 本插件在这里读掷骰记录，并和步骤 1 记下的文本核对

如果 `priority` 大于 20000，第 1 步就会发生在掷骰之后，**掷骰永远无法计分**。所以这个数字不能改。

### 4. 本插件不会拦截消息

本插件**绝不调用 `plugin_event.set_block()`**。OlivOS 的插件事件是逐个调用、不中断的，只有主动 block 才会截断后续插件 —— 一旦 block，青果的骰子就失效了。本插件只是「顺便看一眼」，所有指令照常传给 OlivaDiceCore。

## 三、快速上手

**骰主**（在打算当后台群的群里发）：

```
【PVP】注册后台群 尽伏诛
【PVP】添加管理 你的管理QQ号
```

**后台管理员**（可以继续在后台群发）：

```
【PVP】设置活动日期 活动周期：2026-09-01 ~ 2026-09-02 每日开放：14:00 ~ 18:00
【PVP】设置初始血量 200                   ← 新玩家出生血量
【PVP】设置血量上限 500                   ← 血条能有多长（回血封顶），可高于初始血量
【PVP】设置初始铜币 1000
【PVP】设置初始攻击 50                    ← 全体统一的基础攻击值
【PVP】设置个人攻击 张三 60                ← 只给某人单独设（写 0 清除）
【PVP】设置主动次数 3
【PVP】设置回合数 10
【PVP】设置每种道具限用 1
【PVP】设置伤害表 大成功=20 极难成功=15 困难成功=10 成功=5 失败=0 大失败=0
【PVP】注册玩家 群号 QQ号 玩家名        ← 给每个玩家注册，并指定他的个人群

**玩家**（在自己的个人群里）：

```

然后按机器人提示走：声明道具 → 逐条发 `.raN` → 等战报。

## 四、数据文件

数据落在 **OlivOS 运行目录**下：

```
plugin/data/pvp/
├── 游戏.json      游戏名、后台群、管理员名单
├── 配置.json      活动配置、伤害表、商城价格
├── 玩家.json      玩家档案（血量、铜币、背包、每日次数、可选个人攻击值）
├── 队列.json      排队中的 PVP 请求
├── 对局.json      进行中的对局
└── 战报.json      最近 500 场战报（自动淘汰最旧的）
```

几点说明：

- **不含 `data/` 子目录**是刻意的。青果在升级插件时会清空并重建 `plugin/data/<命名空间>/data`，数据放那里会被误删。
- 每个文件写入都是**原子写**（先写 `.tmp` 再 `os.replace`），并保留一份 `.bak`。写坏了会自动从 `.bak` 回退，不会因为一次异常写坏整个玩家表。
- 配置文件是**可以直接手改**的（改完在机器人里发 `【PVP】配置` 可核对）。所有配置项见指令手册第七节。

## 五、关键设计决策

### 掷骰结果怎么拿到：读记录 + 自己判等级，**不解析回复文本**

青果的 `.ra` 会把这次掷骰写进用户配置（`onediceOverride.py`）：

- `RDRecordInt` —— 这次掷出的骰值
- `RDRecordSkillInt` —— 这次用的技能值（`.ra50` 里的 `50`）

所以本插件读这两个值，再用 `OlivaDiceCore.skillCheck.getSkillCheckByTemplate` 自己算成功等级 —— 这和 `.ra` 内部用的是**同一个函数**，结果完全一致。

**为什么不解析回复文本看「成功/失败」？** 因为青果的所有回复文案都是用户可改的（GUI 里能改，也能用 `.strPcSkillCheckFailed 哈哈失败哈哈` 直接改，模板里还能写 `|` 做随机分支）。任何靠正则抠文案的方案都会在用户改完文案后静默失效，而且失效得很隐蔽。

### 防作弊：核对「本回合应该掷多少」

玩家想掷 `.ra99` 提高成功率会被拦下。核对的是**本回合**的要求值（不是本场的基础值），因为回合型道具会让不同回合的 `.raN` 不同。掷错了不计数，重掷时仍然补记到同一个回合。

另外还比对「玩家自己敲的数字」和「记录里的技能值」—— 不一致说明这条记录是上一次掷骰的残留，直接忽略，否则会把旧结果当成新结果计分（等于直接算错血量）。

### 状态不落盘，从血量现算

玩家状态（正常 / 濒死 / 死皮）**在任何地方都不是独立存的字段**，永远由当前血量推导：

| 血量 | 状态 |
| --- | --- |
| > 20 | 正常 |
| 1 ~ 20 | 濒死 |
| = 0 | 死皮 |

这样管理员用 `【PVP】修改血量 张三 150` 把人救回来时，状态自动跟着变，不存在「血满了但还是死皮、什么都干不了」的不一致。

### 跨群推送必须自己排队

海豹（Shiki）对主动消息会自动排队，青果**不会** —— 超频直接返回失败，消息就没了。而 QQ 平台限制单群 20 条/分钟。一场 PVP 结算要在两个群各发一条战报，一晚上几十场就是上百条。

所以跨群推送一律走本插件的队列，后台线程按「每群每分钟不超过 18 条」的滑动窗口匀速发出。**回复当前群不走队列**（那条路径由青果自己处理被动消息，走队列反而会让玩家觉得反应慢半拍）。

### 昵称显示与匿名规则

被发起人**全程不知道发起人是谁**（PRD 4.3.3 / 验收标准 13）。所有发给被发起人的消息都用「神秘对手」代替发起人名字，包括：

- 匹配通知
- 战报（`神秘对手 累计造成伤害：30`）
- 死亡掉落播报（`…归 神秘对手：777 铜币`）

因此所有双群播报的接口都要求**两条文本分开传**（`_sendToBothSides`），不允许图省事让两边共用一条文本 —— 那会造成「B 收到了 A 的名字」这种上线后极难发现的泄露。

## 六、相对 PRD 的扩展与差异

以下是本插件与 PRD 原文**不完全一致**的地方，都是有原因的选择，请重点复核。

### 6.1 新增的指令（PRD 指令表里没有）

| 指令 | 为什么必须补 |
| --- | --- |
| `【PVP】血量` / `【PVP】战报` | PRD 2.2 权限矩阵写了玩家可「查看本人血量/战报」，但 5.3 指令表里没有对应指令，玩法上是断的。补这两条 |
| `【PVP】排队` | 玩家需要知道自己在排队第几位 |
| `【PVP】帮助` | 避免玩家必须翻文档 |
| `【PVP】强制结束` | PRD 3.2 把「管理强制终止」列为对局结束途径，但 5.2 没有对应指令。且 PRD 4.4/8 **没有声明超时**，玩家不掷骰时对局会永远卡住 —— 必须有个兜底出口 |
| `【PVP】设置道具价格` | PRD 没给商城价格也没给改价指令，默认价写死在代码里。补一条让场控能调价 |
| `【PVP】发放道具` / `【PVP】回收道具` | 否则道具只能靠购买获得：开服福利、活动奖品、误操作修正都做不了 |
| `【PVP】删除玩家` | 注册错了的玩家需要能摘掉（会一并清掉他的队列请求与进行中的对局） |
| `【PVP】配置` / `【PVP】名单` | PRD 2.2 写了骰主/管理可「查看活动配置 / 查看全量数据」，指令表里没有入口 |
| `【PVP】管理` | 管理指令已有 20+ 条，谁都不可能背下来。补一条自描述的入口：正文从代码路由表现场生成，所以不会出现「文档里有、实际没有」或反过来的过期问题 |
| `【PVP】设置声明超时 N` | 声明超时是本插件的扩展行为（见 6.2），得有个指令能调 |
| `【PVP】购买 道具名 数量` | 数量参数是扩展，不填默认 1 |

### 6.2 行为上的差异

| 位置 | PRD 原文 | 本插件实现 | 原因 |
| --- | --- | --- | --- |
| 道具声明 | 4.4 的模板像是「一次声明一件」 | **可连续发送多条声明**，最后发 `【PVP】不使用` 结束 | PRD 4.2 允许把「每种道具限用」配成大于 1，那就必须能连续声明多件，否则该配置永远不可能生效。**这是 PRD 模板的严格超集**，只声明一件的用法完全不变 |
| 设置初始铜币 | 未说明作用范围 | **只影响之后注册的玩家**，不重置已有玩家钱包 | 若做成「全体重置」，一次手滑就把全场经济清零 |
| 血量两个配置项（➕ 扩展） | 4.7.1 写死「初始血量 = 上限 = 200」 | 拆成两条指令：`【PVP】设置初始血量 N`（新玩家出生血量）与 `【PVP】设置血量上限 N`（血条长度：回血封顶、夹取上界、显示分母），都是 1 ~ 100000，出厂值都为 200 | 这是同一件事上的两个不同数值：起始值决定新号从多少血起步，上限决定血条最长能有多长。常见设法是上限高、初始低（上限 500 / 初始 200），给玩家留成长空间 —— 合成一个数就做不到这件事 |
| 个人攻击值（➕ 扩展） | 4.2 只有「全体统一初始攻击」 | 新增 `【PVP】设置个人攻击 玩家名 N`，**个人值优先、未设定的回落统一值**，写 `0` 清除；`【PVP】设置初始攻击 玩家名 N` 是同义便捷写法 | 开团时总有个别玩家需要单独调（新手照顾、惩罚、剧情设定）。若建档时把统一值抄进档案，骰主之后改统一值就对老玩家完全不生效，看起来像「设置了没用」——所以档案里只在被单独指定过时才有该字段 |
| 每回合 `.raN` 的上下界 | 未说明 | 生成掷骰计划时夹到 **1 ~ 100** | 青果 `.ra` 的判定骰值就是 1~100：低于 0（错影符叠加）或高于 100（攻击值 100 再叠胜临符 +10）都是非法指令，玩家照着掷骰列表发出去会毫无反应 |
| 满血使用大还丹 | 未说明 | **拒绝，且不消耗道具** | 避免白白扣掉一件道具 |
| 解毒丸 / 幻息丹 | 「预留」/「效果待定」 | **拒绝使用，且不消耗** | 这两件在本次规则里没有实际作用，用了白扣是纯粹的负体验，且容易被当成 bug 报上来 |
| 属性修改上限 | 未说明 | 回合数 ≤ 100、单次数值 ≤ 1 亿、血量 ≤ 当前上限 / ≥ 0、攻击值 1 ~ 100 | 防止手滑多打几个 0 把机器人拖死 |
| 死亡掉落播报里的名字 | 未说明格式 | 掉落播报也走匿名规则（发起人显示为「神秘对手」） | 掉落文案是两边共用的同一条，不处理就会泄露发起人身份 |
| `结束活动` 的残留文件 | 「删除所有数据」 | 删掉游戏/玩家/队列/对局/战报五个文件；**配置.json 重写为默认值** | 配置里存着 `master_id`（骰主身份兜底），它与本次活动无关，删掉会让骰主在重启后失去骰主权限。活动配置本身已重置为默认值 |
| 发起回执 | 未定义回执格式 | 只回「已收到 PVP 请求，排队中。」；有对局正在打时追加一行说明 | 回执要交代「接下来会发生什么」。若只回干巴巴的一句，玩家分不清「在排队」和「卡住了」 |
| 声明阶段超时 | PRD 4.4 / 8 无超时 | **默认 10 分钟自动取消**（`declare_timeout_minutes`，配 0 关闭）：不结算、血量背包维持、道具与主动次数返还，队列立刻顶上；**取消时给双方各发一条通知**，写明「因为超时未完成道具声明」 | 没有超时的话，一对玩家都放着不声明，对局永远卡在声明阶段，队列里后面所有人的请求永远轮不上 —— 这是「排队中之后再无下文」的根源。通知双方是必须的：否则玩家那边只是对局凭空消失，谁也不知道为什么。管理仍可用 `【PVP】强制结束` 立即终止 |
| 跨群消息发送失败 | 未说明 | **自动重试（最多 3 次）+ 账号兜底**：找不到登记账号时改用其它可用账号发，重试耗尽才丢弃并打日志 | 跨群推送是对局的唯一通知渠道，发丢了玩家就永远不知道该声明道具，表现为对局「卡住」。而发送失败往往是瞬时的（重载后 Proc 未就绪、重连中），重试能救回来 |
| 掷骰阶段超时 | PRD 4.5 / 8 无超时 | **默认 30 分钟按已有记录结算**（`fight_timeout_minutes`，配 0 关闭）：缺的回合按 0 伤害计，战报注明谁缺几回合 | 掷骰阶段的任何一掷被防作弊 / 旧记录防护拦下而没补掷，那一方就永远少一格，双方「都掷满」的结算条件永远不成立 —— 对局无声卡死，谁也等不到「等待结算」和战报。已经打了一部分，取消会丢账，所以是结算而不是取消 |
| 掷骰回执 | PRD 6 模板只有「第 N 回合已记录」 | **一条掷骰只回一条**「第 N 回合已记录：值（等级）」，不显示进度；掷骰前不再额外发「现在是第 N 回合，请发 .raX」引导；自己掷满时提示「你的 N 回合已全部掷完，等待对方掷骰。」；双方掷满时提示「N 回合已全部掷完，等待结算」 | 曾按「进度要看得见」的思路加过双方进度和掷前引导，实机上一次掷骰会冒出两条插件消息、且进度数字对玩家无用。少掷的风险改由掷骰超时兜底（按已有记录结算并在战报注明缺回合），不需要靠回执里的进度来暴露 |
| **在场玩家的下文走会话直发** | 未说明投递通道 | 排到通知、声明引导、掷骰列表、战报：**谁正在跟机器人说话，谁的那份直接回在他的会话里**；不在场的另一方用**发起人/掷骰者的活事件直发到对方群**（`jfzSend.sendViaEvent`）。纯后台场景（时段取消、超时结算、重启恢复）没有事件触发者，则复用**最近一条活事件**发送（`jfzSend.rememberEvent`），只有连缓存都没有时才现造 fake 事件 | 真机排查发现：跨群推送链路长（自建队列 → fake 事件 → control_queue → link 进程），任何一环静默失败，玩家的表现就是「机器人回了一句就再无下文」。活事件的 bot_info / control_queue 由框架在 `run_plugin` 里填好，且 `Event.send` 走 `force_active=True` 不校验事件本身是否过期，所以缓存复用是安全的（按 botHash 分桶，多账号不会串号） |
| 管理指令权限 | PRD 2.2 矩阵里「配置活动参数 / 发放扣除铜币」骰主是 ✖ | **骰主拥有后台管理员的全部权限**（骰主 ⊇ 管理员） | 骰主是这台机器人上权限最高的人，不该出现「想调活动参数得先把自己加成管理员」这种绕一圈的操作 —— 而且「添加管理」这个入口本身也只有骰主能开。玩家权限不受影响 |
| 战报内容 | PRD 6 模板含双方剩余血量 | **不展示双方剩余血量**，只列累计造成伤害与胜负 | 战报会被群成员围观、被截图转发，剩余血量是个人状态数据，不该长期留痕；要查血量有 `【PVP】血量` |
| 玩家表缺失时的跨群推送 | 静默跳过 | **打警告日志**（玩家不在玩家表 / 没登记群号），并且发送层每次成功发出都打一行「跨群推送已发出」日志 | 「静默跳过 + 静默失败」叠加起来，真机上出了问题完全无从排查 —— 控制台一片安宁，玩家那头没有任何下文 |
| `设置活动日期` 的参数格式 | PRD 5.2 写的是 4 个裸值：`开始 结束 每日开始 每日结束` | 改成带标签的可读格式：`活动周期：2026-09-01 ~ 2026-09-02 每日开放：14:00 ~ 18:00`；解析**不按位置切词**，而是直接扫出「日期样 / 时间样」的片段各取前两个 —— 波浪线前后空格可省、标签可省、「每日开放」写在前、中文「至 / 到」都认；回执与用法提示里都会带上这个示例 | 4 个裸值看不出哪个是哪个（`2026-09-01 2026-09-02 14:00 18:00` 里两组值长得完全不一样，但 `14:00 18:00` 到底是「每日开放」还是别的，全靠位置暗示）。带标签的写法一眼可读；而只要按位置切词，用户任何一种换写法都会被判「格式不对」，于是改成按内容识别 |

### 6.3 原样照抄、刻意未改的地方

- **没有「复活玩家」指令**（PRD 2.1 明确），统一用「修改血量」，状态自动重算。
- **声明阶段默认有 10 分钟超时、掷骰阶段默认有 30 分钟超时**（都可配 0 关闭回到 PRD 原行为）。PRD 未定义超时，但实机上「无人声明 / 没掷满」会让对局无声卡死并堵死队列，所以默认开启，配置可关。
- **被发起人不能拒绝挑战**（PRD 未定义拒绝流程）。收到匹配通知即进入声明阶段。
- **没有把动态文案做成可编辑模板**：排队提示、掷骰列表、战报里都要填血量、骰点、伤害合计等运行期数据，做成模板后用户改坏占位符的维护成本大于收益。真正需要用户改的（活动配置、伤害公式、商城价格）都做成了指令。

### 开发过程中被测试抓出并修掉的问题

以下都是「逻辑看着对、真跑就错」的问题，列出来说明测试的价值：

1. **`getPlayerByGroup()` 返回值被当成玩家名用** —— 它返回的是玩家档案 dict，而骰子钩子和掷骰提示里都把它当玩家名传给了 `getPlayer()`，于是 `getPlayer(dict)` 稳定返回 `None`，被误判成「这个人不是本群登记的玩家」，**导致所有掷骰都不计分**。已补一个语义独立的 `getPlayerNameByGroup()` 并把两个混淆点分开。
2. **`【PVP】强制结束` 路由到不存在的函数** —— 实现在 `jfzEngine`，路由表却指向 `jfzAdmin`。这会导致 `AttributeError`，而该异常被 `main` 的 try 吞掉，现象是「发了指令毫无反应」。
3. **`配置` / `名单` 有实现但没进路由表** —— 发出来只会收到「不认识的指令」。
4. **`配置` / `名单` 的处理函数只接受 1 个参数** —— 分发器统一按 2 个参数调用，同样表现为「毫无反应」。
5. **骰主 ID 兜底读错了键名** —— 判定代码读 `'骰主ID'`，配置里存的是 `'master_id'`，这段兜底从来没生效过。
6. **掉落播报泄露发起人身份** —— 掉落文案原本两边共用一条，被发起人可以从掉落那一行读到发起人真名。
7. **被发起人侧匹配通知缺「神秘对手」占位** —— 直接省略了发起人行，与 PRD 6 的模板形状不符。
8. **`结束活动` 后用空内容把 `游戏.json` 写了回去** —— 骰主翻数据目录时看到残留文件，会以为没删干净。
9. **跨群推送发送失败被静默丢弃** —— 发送层找不到账号 / Proc 未就绪时只打一行日志就把消息丢了，而跨群推送是对局的唯一通知渠道：匹配通知发丢，双方就永远不知道要声明道具，对局表现为「卡住」。已改为失败自动重试（最多 3 次）+ 找不到账号时用其它可用账号兜底发送。
10. **测试自身的问题**：跨群推送断言查了「会话回复」日志而不是「出站消息」日志；`drain()` 只等队列空、没等消息真正落地，导致断言随机失败；各阶段之间道具与每日次数没复位造成状态污染。这些已一并修正，现在连续跑多次结果稳定。

## 八、排障

### 发什么指令都回「不认识的指令」

还没注册游戏。让骰主先发 `【PVP】注册后台群 游戏名`。

### 骰主说「仅限骰主」但自己明明是骰主

在 QQ 官方机器人（openid）环境下，青果骰主名单里存的 userHash 可能与收到的 userId 对不上。用不依赖任何权限的入口兜底 —— 直接编辑配置文件：

```
plugin/data/pvp/配置.json
```

把 `"master_id"` 改成你的 QQ 号 / userid，重启插件即可。

> 之所以不做成一条指令，是因为「设置骰主ID」这条指令本身要先过骰主校验 —— 在骰主校验已经失效的环境里没人能执行它。

### 掷了 `.raN` 但没计分

按可能性从高到低排查：

1. **技能值和机器人给的列表不一致** —— 机器人会明确提示「掷骰值与要求不符，请重新发送 .raN」
2. **用了连掷或奖励骰** —— `.ra50#3`、奖励骰/惩罚骰的骰值是元组而不是单个数字，读不到结果，会提示「这一掷没被记录」
3. **掷骰记录是上一次的残留** —— 命令里的数字和记录里的技能值对不上时会提示「未被记录」，重掷即可
4. **不在掷骰阶段** —— 还在道具声明阶段时掷骰不会计分，机器人会提示
5. 还是不行的话，用 `python3 debug_gate.py` 逐关打印钩子的判定过程（见该文件头部说明）

> 每一掷的回执都带「进度：你 X/N，对方 Y/N」，`【PVP】排队` 也会显示双方进度。
> 对局迟迟不结算时先看进度 —— 多半是有人少掷了一掷。
> 实在没人补掷，掷骰超时（默认 30 分钟）会按已有记录结算；急着打可以让管理 `【PVP】强制结束`。

### 跨群消息来得慢

单群每分钟最多推 18 条，超出的会排队等下一个窗口。这是为了不触发 QQ 平台的限频，属于预期行为。一场完整对局约推 5 条（匹配、声明引导、掷骰列表、战报等）。

### 跨群消息完全发不出去

发送层对失败消息会**自动重试 3 次**，且找不到登记账号时会改用其它可用账号兜底，
所以真机上偶发一条 `警告：找不到账号 xxx，改用账号 yyy 发送` 属于兜底成功，不用管。

如果日志里出现 `★★ 消息重试 3 次仍失败，已丢弃`，按内容排查：

- `插件托盘进程还没准备好` —— 插件刚重载完的那几秒，重试通常已经救回；仍出现说明青果的插件进程没起来
- `账号表里一个可用账号都没有` —— 机器人的账号没配置好，或 OlivOS 的 `bot_info_dict` 为空
- `发送异常` 并跟着堆栈 —— 协议端通道问题：QQ 官方机器人需要 `flag_from_qq` 等标记（本插件已自动处理，按 `app.json` 的 sdk 名判断），NapCat 通道不需要

### 插件加载失败

检查机器人日志里的报错：

- `No module named 'OlivaDiceCore'` —— 青果骰子没装或没启用，本插件依赖它
- 语法错误 —— 确认 Python 版本符合 OlivaDiceCore 自身的要求（本插件本身只用标准库，没有额外的版本门槛）

## 十、修改约定

- **所有回复文本里的 `【尽伏诛】` 一律用 `jfzCore.gameTag()` 生成**，不要写字面量 —— 游戏名是骰主可改的。
- **任何改动后跑一遍** `pvp_tests/run_tests.py`，它会顺带检查路由表完整性。
- 新增管理指令时，注意三件事一起改：`jfzReply` 的路由表、`jfzAdmin` 的处理函数（**形参必须是 `(plugin_event, args)`**）、`msgCustom` 帮助文档。少任何一处，测试都会失败或在真机上表现为「发了没反应」。
